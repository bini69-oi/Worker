# Правила для ИИ-агентов

Этот файл читает любой ИИ-агент перед работой с Worker. Процесс целиком описан в [docs/development.md](docs/development.md),
почему устроено так, в [docs/decisions.md](docs/decisions.md).

## С чего начать

1. Найди текущее изменение в `openspec/changes/` (не `archive`). В нём `proposal.md` (зачем), `design.md` (как), `specs/` (что должно работать), `tasks.md` (по шагам).
2. Возьми первую невыполненную задачу из `tasks.md`. Одна задача за раз.
3. Прочитай спеку, к которой она относится, и код рядом. Не угадывай: функция ядра, тип или текст уже могут существовать.

## Как делать задачу

1. Тест первым. Он повторяет сценарий из спеки и падает.
2. Код, пока тест не позеленеет. Ровно столько, сколько нужно задаче.
3. `make check` зелёный (gofmt, vet, staticcheck, тесты с `-race`). Для фронта ещё `make web-check`.
4. Отметь задачу `[x]` в `tasks.md`.
5. Одна задача = один коммит. Сообщение по-русски: что теперь умеет код.

Не получилось за разумное время, спека противоречит коду или задача больше 2 часов: остановись и опиши, что мешает. Не обходи.

## Законы

- **Логика только в `core`.** Бот, API и фронт показывают данные и зовут функции ядра. Проверки прав, денег и владельца объекта живут в ядре.
- **Деньги целыми копейками** (`int64`). Никаких `float` для денег.
- **Время через `Clock`**, не `time.Now()` в ядре.
- **SQL только в `store`.** Панель только через очередь `outbox`, сценарий не зовёт панель напрямую.
- **Тексты только по ключу** из `texts`. В коде бота и фронта нет строк, которые видит абонент.
- **Настройки только из реестра** `settings`. Новая настройка: ключ, тип, умолчание, описание, группа.
- **Секреты не печатаются.** Ни в журнал, ни в ошибку, ни в тест. Всё, что выводится наружу, идёт через `redact`.
- **Действие админа** проверяет права и пишет журнал в той же транзакции (`asAdmin` в `core`).
- **Новая зависимость** только с записью в `docs/decisions.md`. Сначала смотри стандартную библиотеку.
- **Файл до ~300 строк, функция делает одно дело.** Разросся, раздели по смыслу.
- **Горутина с выходом.** Каждая горутина завершается по `ctx`, у каждой очереди есть предел.
- **Ошибка, которую видит человек,** имеет код из `core/errors.go`.

## Где что лежит

| Папка | Что внутри |
|---|---|
| `core` | типы и сценарии, интерфейсы `Store`, `Panel`, `Clock`, `Notifier` |
| `store` | SQLite: миграции и запросы |
| `panel` | клиент Remnawave |
| `pay/<касса>` | касса одним файлом, общий набор тестов `pay/gatewaytest` |
| `tg` | клиент Telegram Bot API |
| `bot` | экраны текстового бота, по файлу на экран |
| `api` | HTTP API для кабинета и админки |
| `web` | фронт на Svelte: `web/src/app` кабинет, `web/src/admin` админка, `web/src/lib` общее |
| `jobs`, `settings`, `texts`, `redact`, `tgsign`, `guard` | фоновые задачи, настройки, тексты, чистка секретов, подписи Telegram, защита HTTP |

## Тесты

- Без сети. Telegram, панель и кассы заменяются фейками или `httptest`.
- Таблицы сценариев: имя случая, вход, ожидание.
- Экраны бота и ответы API сверяются с эталонами в `testdata/` (golden-файлы). Обновить эталон: `go test ./bot -update`. Изменение эталона смотрится глазами в диффе.
- Разбор чужого ввода (данные кнопок, диплинки, вебхуки, JSON от фронта) покрыт fuzz-тестом.
- Тест не печатает секреты и не зависит от порядка и времени запуска.

## Перед тем как сказать «готово»

- `make check` зелёный, новые сценарии спеки покрыты тестами.
- Нет новых предупреждений линтера. «Известных» предупреждений не бывает.
- Ввод снаружи проверен на границе: длина, формат, диапазон.
- Ошибка внешней системы не роняет процесс и не теряет деньги.
- Ты перечитал свой дифф целиком.

## Чего не делать

- Не дублировать логику ядра в боте, API или фронте, даже «временно».
- Не ловить ошибку молча. Либо обработать, либо вернуть наверх.
- Не менять чужие файлы ради своей задачи без причины в описании коммита.
- Не трогать `store/migrations/` уже вышедшей версии: новая миграция новым файлом.
- Не придумывать поведение, которого нет в спеке. Нет в спеке, значит, вопрос.
