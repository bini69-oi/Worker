# Design

## Context

Репо пустое, пишем с нуля. Зачем нужно ядро, сказано в `proposal.md`. Что оно должно делать, сказано в спеках `specs/*`.
Ограничения из `docs/decisions.md`: Go, один процесс, SQLite, логика только в ядре, деньги в копейках.

## Goals / Non-Goals

**Goals:**
- Ядро, которое можно целиком проверить тестами без сети, без Telegram и без настоящей панели.
- Код, который новичок читает сверху вниз: папка = одна тема, файл до ~300 строк.
- Один процесс с памятью до 50 МБ на 10 тысяч абонентов.

**Non-Goals:**
- Несколько копий процесса на разных серверах. Один процесс на одну базу.
- Другие панели кроме Remnawave.
- Готовый HTTP API для фронта. Он будет в части Mini App.

## Decisions

### Папки

| Папка | Что внутри | Зависит от |
|---|---|---|
| `cmd/worker` | `main.go`: читает `.env`, собирает всё и запускает | всё |
| `core` | типы (абонент, тариф, подписка, платёж) и сценарии (`Buy`, `Extend`, `Trial`, `Credit`, `ApplyPromo`) | только интерфейсы `Store`, `Panel`, `Clock` |
| `store` | SQLite: миграции и запросы | `core` (типы) |
| `panel` | HTTP-клиент Remnawave и проверка его вебхуков | `core` (типы) |
| `pay` | интерфейс кассы и реестр касс | `core` (типы) |
| `pay/yookassa`, `pay/stars`, ... | по папке на кассу | `pay` |
| `jobs` | планировщик и фоновые задачи, по файлу на задачу | `core` |
| `settings` | реестр настроек и кэш | `store` |
| `texts` | тексты по ключам и подстановки | `store` |

`core` не импортирует ни `store`, ни `panel`. Он объявляет интерфейсы, которые ему нужны, а `cmd/worker` подставляет реализации.
**Почему:** так ядро тестируется с фейками в памяти. Альтернатива «ядро зовёт SQL напрямую» быстрее писать, но её не протестировать без базы, и через год логика расползётся по запросам.

### Таблицы

| Таблица | Главные поля | Зачем |
|---|---|---|
| `users` | id, tg_id, lang, referrer_id, balance, created_at | абонент |
| `tariffs` | id, name, traffic_bytes, devices, reset, squads (JSON), active, sort | тариф |
| `tariff_periods` | tariff_id, days, price | цены по срокам |
| `subscriptions` | id, user_id, tariff_id, period_days, price, panel_uuid, expires_at, auto_renew, status | подписка, цена заморожена |
| `ledger` | id, user_id, amount, reason, ref_type, ref_id, admin_id, comment, created_at | каждое движение денег |
| `payments` | id, user_id, gateway, amount, status, external_id, created_at, paid_at | все платежи всех касс |
| `outbox` | id, kind, payload (JSON), attempts, next_at, last_error, done_at | задачи к панели и уведомления |
| `promo_codes` / `promo_uses` | код, вид, значение, лимиты / кто и когда | промокоды |
| `pending_buys` | user_id, tariff_id, days, created_at | умная корзина |
| `settings` | key, value | только отличия от умолчаний |
| `texts` | key, lang, value | только изменённые тексты |
| `notices` | user_id, kind, ref, sent_at | чтобы напоминание не ушло дважды |

`users.balance` это кэш суммы `ledger`. Он меняется только в той же транзакции, что и строка `ledger`.
**Почему:** баланс читается часто, а считать сумму каждый раз дорого. Тест сверяет кэш с суммой.

### Деньги не зачисляются дважды

1. `payments.external_id` уникален для кассы (`UNIQUE(gateway, external_id)`).
2. Зачисление делает условное обновление `UPDATE payments SET status='paid' WHERE id=? AND status='pending'`. Если затронуто 0 строк, платёж уже зачислен, выходим.
3. В той же транзакции пишется строка `ledger` с `ref_type='payment'` и `UNIQUE(ref_type, ref_id)`.

**Почему:** два независимых замка. Даже если вебхук и сверка придут в одну миллисекунду, второй упрётся в условие или в уникальный ключ.
У SQLite один писатель, это дополнительно упрощает дело.

### Очередь к панели (outbox)

- Сценарий ядра в одной транзакции меняет подписку и кладёт строку `outbox` вида `panel.sync_user` с id подписки.
- После коммита задача сразу отдаётся воркеру через канал. Воркер раз в секунду также забирает задачи с `next_at <= now`.
- Задача не несёт «продли на 30 дней». Она несёт «приведи абонента в панели к состоянию из базы». Поэтому повтор безопасен (спека `panel-sync`).
- Пауза между попытками: 5 с, 30 с, 2 мин, 10 мин, дальше каждые 30 мин. Через час уведомление админу.

**Альтернатива:** звать панель прямо из сценария и при ошибке откатывать. Отказались: если панель ответила «ок», а ответ потерялся, база и панель расходятся.

### SQLite

- Драйвер `modernc.org/sqlite` (чистый Go, без CGO), поэтому бинарник собирается под любую платформу одной командой.
- Режим WAL, `busy_timeout=5000`, `foreign_keys=ON`.
- Одно соединение на запись, пул на чтение. **Почему:** SQLite пишет по одному, так мы не ловим `database is locked`.
- Миграции это файлы `store/migrations/NNN_name.sql`, вшитые через `embed`. Номер применённой хранится в `PRAGMA user_version`.
- Запросы пишем руками в `store/*.go`. **Почему не ORM:** запросов немного, SQL читается проще, чем ORM.

### Кассы

```go
type Gateway interface {
    Name() string
    Create(ctx, Payment) (Invoice, error)       // ссылка или счёт
    Verify(r *http.Request) (Event, error)      // проверить подпись вебхука
    Status(ctx, externalID string) (Status, error)
}
```

Касса регистрируется в `pay` при старте. Вебхук всех касс один: `POST /pay/{name}`.
Общий набор тестов `pay/gatewaytest` прогоняет каждую кассу на поддельной подписи, повторе и неверной сумме.

### Настройки и тексты

- Реестр это список в коде: ключ, тип, умолчание, описание, группа, секретная или нет.
- Значения из базы читаются в память при старте и перечитываются раз в 3 секунды по `MAX(updated_at)`. **Почему не уведомления об изменении:** процесс один, опрос дешёвый и простой.
- Секреты шифруются AES-GCM ключом из `.env`.
- Тексты устроены так же: умолчания в коде (`texts/default_ru.go`), изменения в базе.

### Время

Ядро получает время через интерфейс `Clock`. Тесты двигают время руками.
**Почему:** окончание подписки, напоминания и автопродление без этого не протестировать.

### Ошибки

У ошибок, которые видит абонент, есть код `E` + 4 цифры (`E2001` значит «не хватает денег»). Коды собраны в один файл `core/errors.go`.
Абонент видит текст по ключу и код, админ по коду находит запись в журнале.

### Журнал

`log/slog` в JSON. Ключи касс и токены в журнал не пишутся никогда, это проверяет тест.

### Тесты

- Ядро: таблицы сценариев на фейковых `Store`, `Panel`, `Clock` в памяти.
- `store`: на настоящей SQLite во временном файле, той же, что в проде.
- `panel`: на `httptest.Server`, который отвечает как Remnawave 2.x и 3.x.
- Кассы: общий набор `gatewaytest` и записанные примеры вебхуков.
- Проверка перед коммитом: `gofmt`, `go vet`, `staticcheck`, `go test -race ./...`.

## Risks / Trade-offs

- [SQLite упрётся в запись при большом росте] → один писатель держит тысячи транзакций в секунду, бот делает единицы. При реальной нужде `store` можно переписать под Postgres, ядро не изменится.
- [Сверка откатывает ручные правки в панели] → в документации прямо пишем: продлевать надо через Worker. Расхождение видно в журнале.
- [Опрос настроек раз в 3 секунды] → правка видна не сразу, но в пределах 5 секунд из спеки.
- [Кассы меняют API] → у каждой кассы записанные примеры вебхуков в тестах, поломка видна сразу.
- [Чистый Go-драйвер SQLite медленнее CGO-версии] → на нагрузке бота разница незаметна, зато сборка простая.

## Migration Plan

Миграций нет, это первая версия. Откат: остановить процесс и удалить файл базы.
