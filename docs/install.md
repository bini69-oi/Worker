# Установка на сервер

Worker ставится одной командой на чистый сервер с Debian 12+ или Ubuntu 22.04+ (amd64 или arm64). Нужен OpenSSL 3 (он есть в Debian 12+ и Ubuntu 22.04+): через него проверяется подпись релиза. Debian 11 не поддерживается, там OpenSSL 1.1.1 не проверяет Ed25519, а ставить без проверки подписи установщик не будет. Docker не нужен.

## Что понадобится

- сервер, на котором вы root или можете `sudo`, с программами `curl`, `openssl`, `systemctl` (на Debian и Ubuntu они есть;
  для Caddy нужен ещё `gpg`: `apt install gnupg`);
- домен, у которого A-запись уже смотрит на адрес сервера;
- токен бота от [@BotFather](https://t.me/BotFather);
- ваш Telegram ID (число, его покажет [@userinfobot](https://t.me/userinfobot));
- адрес панели Remnawave и её API-токен.

## Команда

```sh
curl -fsSL https://raw.githubusercontent.com/bini69-oi/worker/main/install/install.sh | sudo bash
```

Запускайте в терминале: установщик задаёт вопросы. Если подключаетесь по ssh, добавьте `-t`.
Версию можно выбрать: `... | sudo bash -s -- --version v1.2.3`.

## Что делает установщик

1. Проверяет систему и архитектуру.
2. Скачивает релиз и проверяет подпись списка сумм вшитым ключом, потом сумму бинарника.
   Не сошлось: установка останавливается, на сервере ничего не изменено.
3. Спрашивает данные и проверяет каждый ответ сразу, неверный спрашивает заново:

   | Вопрос | Как проверяется |
   |---|---|
   | токен бота | запросом `getMe` в Telegram |
   | Telegram ID | это число |
   | домен | A-запись смотрит на этот сервер |
   | адрес и токен панели | запросом версии у панели |

4. Создаёт ключ шифрования `SECRET_KEY` и показывает его один раз. **Сохраните его в менеджере паролей.** Без него не открыть
   бэкапы и секреты в базе.
5. Ставит бинарник, пользователя `worker` без прав и службу systemd в песочнице, пишет настройки, запускает службу и ждёт,
   пока она ответит на `/healthz`.
6. Настраивает https: ставит Caddy (см. ниже) или печатает конфиг для вашего nginx.
7. Просит задать пароль владельца для админки.

До шага 5 установщик ничего не меняет на сервере: оборвали на любом вопросе, и сервер как был.

## Где что лежит

| Путь | Что | Права |
|---|---|---|
| `/usr/local/bin/worker` | бинарник | root, 755 |
| `/etc/worker/env` | токены и ключ | 600, владелец `worker` |
| `/var/lib/worker/` | база, замок, бэкапы (`backups/`) | `worker`, 700 |
| `/etc/systemd/system/worker.service` | служба | root |
| `/etc/caddy/Caddyfile` | https для домена (если ставили Caddy) | root |

Служба работает от пользователя `worker`, пишет только в `/var/lib/worker` и слушает только `127.0.0.1:8080`: наружу бот
выходит через Caddy или nginx.

## https: Caddy или ваш nginx

Свободны порты 80 и 443, своего Caddy на сервере нет: установщик ставит Caddy из официального репозитория и пишет
`/etc/caddy/Caddyfile`. Сертификат Caddy выпускает сам.

Порт 80 или 443 занят (например, на сервере панель с nginx), или Caddy уже стоит: установщик **ничего не ставит и ваш
веб-сервер не трогает**. Он печатает готовый кусок конфига nginx для вашего домена. Добавьте его, проверьте `nginx -t`,
перечитайте конфиг и выпустите сертификат (например, `certbot --nginx -d ваш.домен`). Пока https для домена нет, Telegram
не сможет присылать боту сообщения.

## Команды на сервере

Команды читают настройки из `/etc/worker/env` сами. Работающей базой управляйте от пользователя `worker`:

```sh
sudo -u worker worker admin password     # задать пароль владельца
sudo -u worker worker backup             # бэкап прямо сейчас, бота останавливать не нужно
sudo -u worker worker backup --check /var/lib/worker/backups/worker-20261101-030000.db.enc
sudo worker update                       # обновить из подписанного релиза, с бэкапом и откатом
sudo worker version
journalctl -u worker -f                  # журнал
```

## Обновление

`sudo worker update` (или `sudo worker update --version v1.2.3`): скачивает релиз, проверяет подпись встроенным ключом и
сумму, делает бэкап, меняет бинарник и перезапускает службу. Если за 60 секунд `/healthz` не ответил, возвращает прежний
бинарник и перезапускает службу, а причину пишет в вывод. Миграции базы только добавляют, поэтому прежний бинарник
с новой базой работает.

Если HTTP-адрес службы вы меняли (настройка `http.addr`), впишите его в `/etc/worker/env` как `HTTP_ADDR=...`: по нему
`worker update` проверяет службу.

Сменился ключ подписи релизов: `curl -fsSL .../install.sh | sudo bash -s -- --update-binary` заменит бинарник
(база и настройки остаются).

## Бэкапы

Раз в сутки Worker сам делает зашифрованный бэкап в `/var/lib/worker/backups/` и хранит последние `backup.keep`
(по умолчанию 14, настройка в админке). Файл шифруется AES-256-GCM ключом, выведенным из `SECRET_KEY`.
Скопируйте папку `backups/` на другой сервер: бэкап на том же диске не спасёт от потери диска.

Восстановление:

```sh
sudo systemctl stop worker
sudo -u worker worker backup --check /var/lib/worker/backups/worker-20261101-030000.db.enc
sudo -u worker worker restore /var/lib/worker/backups/worker-20261101-030000.db.enc
sudo systemctl start worker
```

`restore` работает только при остановленной службе, проверяет целостность базы из бэкапа и откладывает текущую базу рядом
(`worker.db.before-restore-...`). Испорченный файл восстановление отклоняет, текущая база не тронута. Когда убедитесь, что
всё в порядке, отложенную базу удалите.

## Удаление

```sh
sudo systemctl disable --now worker
sudo rm /etc/systemd/system/worker.service /usr/local/bin/worker
```

Папки `/etc/worker` и `/var/lib/worker` (настройки и база) удаляйте вручную, когда они больше не нужны.
