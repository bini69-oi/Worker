# Как мы разрабатываем

Worker пишется вместе с ИИ. Чтобы код получался простым и без лишних ошибок, работа идёт одними и теми же шагами.
Правила для самого агента в [AGENTS.md](../AGENTS.md).

## Шаги одной части

| Шаг | Что делаем | Результат |
|---|---|---|
| 1. Обсуждение | что нужно абоненту и админу, что не делаем | строки в [features.md](features.md), новые решения в [decisions.md](decisions.md) |
| 2. Спека | изменение OpenSpec: `proposal`, `design`, `specs`, `tasks` | `openspec validate <изменение>` проходит |
| 3. Проверка спеки | читаем сценарии глазами: каждый проверяем тестом, нет противоречий с ядром | правки в спеке до кода |
| 4. Код | задача за задачей из `tasks.md`, тест первым | коммит на задачу, `make check` зелёный |
| 5. Ревью раздела | три взгляда на дифф раздела (ниже) | находки проверены по коду и исправлены |
| 6. Ручная проверка | чек-лист части на тестовом боте | пройден целиком |
| 7. Архив | `openspec archive <изменение>` | спеки части в `openspec/specs/` |

## Почему тест первым

ИИ пишет код, который выглядит правильно. Тест, написанный по сценарию спеки до кода, проверяет, что код делает то,
что нужно человеку, а не то, что агент понял. Если тест сразу зелёный, он ничего не проверяет.

## Ревью тремя взглядами

После каждого раздела `tasks.md` дифф смотрят три независимых проверяющих, у каждого один вопрос:

| Взгляд | Вопрос |
|---|---|
| Правильность | где код делает не то, что сказано в спеке? гонки, повторы, пустые значения, границы |
| Безопасность | что может сделать абонент, чужой админ или поддельный запрос? где утекает секрет? |
| Простота | что можно убрать? где логика повторяется? где функция делает два дела? |

Проверяющему дают код и спеку, а не свой вывод: так он не подтверждает чужую ошибку.
Каждая находка проверяется по коду или тестом, прежде чем её чинить. Ложная находка записывается с причиной и закрывается.

## Как делить работу между агентами

- Одному агенту одна папка или один пакет. Два агента в одном файле мешают друг другу.
- Агенту дают: задачу из `tasks.md`, спеку, папку и что уже проверено. Не дают: «сделай бота».
- Агент не коммитит. Человек смотрит дифф и коммитит сам.
- Широкие задачи («пройди всё ядро») агенты делают плохо. Узкие («касса Platega по `docs/add-gateway.md`») хорошо.

## Эталоны вместо ручной проверки

- **Экраны бота.** Тест шлёт обновление в фейковый Telegram и сравнивает текст и кнопки ответа с файлом в `bot/testdata/`.
  Изменение экрана видно в диффе эталона.
- **Ответы API.** Тест сохраняет JSON ответа в `api/testdata/`. Фронт в своих тестах берёт эти же файлы как ответы сервера.
  Одна правда для обеих сторон.
- **Типы фронта.** `make types` делает `web/src/lib/types.gen.ts` из структур Go. CI падает, если файл устарел.

## Проверки

| Команда | Что проверяет | Где |
|---|---|---|
| `make check` | gofmt, go vet, staticcheck, тесты с `-race` | перед каждым коммитом, CI |
| `make vuln` | известные уязвимости Go и зависимостей | CI |
| `make web-check` | типы Svelte, тесты фронта, размер сборки | перед коммитом с фронтом, CI |
| `make types` | типы фронта совпадают с Go | CI |

## Что значит «готово» для части

- Все задачи `tasks.md` отмечены, `make check` и CI зелёные.
- Каждый сценарий спеки покрыт тестом.
- Ревью тремя взглядами пройдено, находки закрыты.
- Чек-лист ручной проверки пройден на настоящем Telegram и тестовой панели.
- README и документация говорят то же, что код.
